# API reference

Generated by reading every `@router.*` call site under `backend/app/api/`
and the Pydantic schemas each one actually uses — not from FastAPI's
auto-generated OpenAPI doc (still available at `/docs` when the backend is
running; this file is the same information organized as prose, plus the
"why" each route's own module docstring already states). Every route below
is mounted with no path prefix beyond what's shown — `app_factory.py`
`include_router`s each one with its own `prefix` and no additional
`/api` or version prefix.

**Authentication: real, but off by default.** Post-Phase-15:
`backend/app/core/auth.py`'s `get_current_principal` is wired globally onto
every router below except `/health`. With `Settings.auth_enabled=False`
(the default), every request resolves a permissive anonymous principal and
behaves exactly as this file described before auth existed — no header
needed. Set `AUTH_ENABLED=true` plus `API_KEYS` (`.env.example`) to require
a real `X-API-Key` header; two routes additionally require the `approver`
role once auth is enabled: `POST /responses/executed` when its `approval`
field is non-null, and `POST /incidents/{id}/investigate` when
`auto_approve=true`. CORS (`Settings.cors_allowed_origins`, an explicit
allowlist, no wildcard) is unconditional either way. See
`docs/security-checklist.md` §6 for the real test coverage.

All request/response bodies are Pydantic schemas (no raw dicts cross the
boundary, per `docs/architecture.md` §15). Enum values are the lower_snake
string members of `backend/app/schemas/enums.py`.

## `/health`

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/health` | Liveness only — proves the app boots and responds. No dependency check (no DB ping, etc.). |

Response: `{status: str, service: str}` → always `{"status": "ok", "service":
"patient-aware-cyber-resilience-backend"}`.

## `/devices`

Read-only view onto the simulated device fleet (`DeviceRegistry`). No write
endpoints — device state changes only via the scenario runner or the
Response Orchestrator.

| Method | Path | Purpose | Response |
| --- | --- | --- | --- |
| GET | `/devices` | List every device in the registry | `list[DeviceState]` |
| GET | `/devices/{device_id}` | One device's current state | `DeviceState`, 404 if unknown |

`DeviceState` (`backend/app/schemas/device.py`): device id, type,
criticality (`low`/`medium`/`high`), `patient_dependency: bool`, operational
state, network state, plus whatever clinical attributes that device type
carries.

## `/telemetry`

| Method | Path | Purpose | Response |
| --- | --- | --- | --- |
| GET | `/telemetry?device_id=` | Every recorded telemetry reading, optionally filtered to one device | `list[TelemetryReading]` |

Read-only; backed by the in-memory `TelemetryStore`. Returns `[]`, never a
fabricated reading, when nothing has been recorded for the filter. The only
thing that currently writes into this store is `/detections/run-scenario`.
With `REPOSITORY_BACKEND=postgres` it is backed by the `telemetry_readings`
table (a TimescaleDB hypertable when the extension exists).

## `/events`

| Method | Path | Purpose | Response |
| --- | --- | --- | --- |
| GET | `/events?device_id=` | Every recorded network/security event, optionally filtered to one device | `list[NetworkEvent]` |

Same pattern as `/telemetry`: read-only, backed by `NetworkEventStore`,
written to only by `/detections/run-scenario`.

## `/detections`

| Method | Path | Purpose | Response |
| --- | --- | --- | --- |
| POST | `/detections/run-scenario` | Runs one fixed, reproducible attack scenario (seed `42`, a spoofed `set_tidal_volume` command against `ventilator-01` at tick 6) against a fresh device registry, scores the resulting event stream with the loaded model, and returns whatever it detects | `list[DetectionEvent]`, 503 if no trained model artifact exists yet |
| POST | `/detections/score-flows` | Scores 1–1000 real CICIoMT2024-style flow records (all 45 dataset features by column name, for one `device_id`) with the real 19-class XGBoost model (`Settings.real_detector_model_path`); returns every flow's verdict (fine class, family, confidence, optional `DetectionEvent`) and opens one incident per distinct attack type detected | `FlowBatchResponse`; 422 for a missing/non-finite feature, 503 with training instructions if the (gitignored) model artifact does not exist |

This is not a free-form "run any scenario" endpoint — the scenario is
hard-coded (`backend/app/api/detections.py`'s own docstring explains why: no
scenario-authoring API exists yet). A successful call also has side
effects: it records the scenario's telemetry/events into the shared
`TelemetryStore`/`NetworkEventStore` (so `/telemetry` and `/events` can read
them back), creates a real `Incident` per detection via
`IncidentRepository.create`, and enqueues each incident's blockchain
provenance onto the outbox. 503's `detail` tells you the exact command to
train a model (`cd backend && python -m app.cybersecurity.training`).

`DetectionEvent` (`backend/app/schemas/detection.py`): `device_id,
attack_type (AttackCategory), confidence: float, severity_hint, timestamp,
evidence_ref`.

## `/incidents`

| Method | Path | Purpose | Response |
| --- | --- | --- | --- |
| GET | `/incidents` | List every incident | `list[Incident]` |
| GET | `/incidents/{incident_id}` | One incident | `Incident`, 404 if unknown |
| POST | `/incidents` | Create an incident | `Incident`, 201 |

`POST /incidents` request body (`IncidentCreateRequest`): `incident_id: str,
device_id: str, attack_type: AttackCategory, evidence_ref: str, timestamp:
datetime`. 404 if `device_id` doesn't exist in the registry; 409 if
`incident_id` already exists. `evidence_ref` is hashed (never stored raw)
before being enqueued as the incident's blockchain provenance. Note:
`attack_type` and `evidence_ref` are request-only fields carried through to
provenance — the `Incident` schema itself has no `attack_type` field (that
lives on `DetectionEvent`/`ThreatAssessment`).

**Post-Phase-15 additions:**

| Method | Path | Purpose | Response |
| --- | --- | --- | --- |
| POST | `/incidents/{incident_id}/investigate` | Run the real multi-agent pipeline (`IncidentOrchestrator`) end to end for this incident | `CycleResultOut`, 404 if unknown, 503 if the configured LLM backend call fails |
| GET | `/incidents/{incident_id}/evidence` | Real join of agent traces + network events + telemetry + recovery results for this incident's device | `IncidentEvidence`, 404 if unknown |

`POST /incidents/{incident_id}/investigate` body (`InvestigateRequest`,
all fields optional): `auto_approve: bool = false`. Sequences investigate →
threat reasoning → healthcare context → response planning → risk scoring →
policy decision → (approval gate, unless `auto_approve=true`) → execution →
recovery verification → recovery routing, automatically re-investigating
(bounded, currently 2 attempts) if recovery routes to `REOPENED`. With
`Settings.llm_backend` at its default (`"mock"`), this call fails with 503
on the very first agent call — there are no scripted `MockLLMClient`
responses in a real running server — which is the honest behavior for an
unconfigured LLM backend, not a bug. `auto_approve=true` requires the
`approver` role when `Settings.auth_enabled=true` (see the auth note
above). `CycleResultOut`: `incident_id, final_status, reinvestigation_count,
history: list[str], awaiting_approval_decision: PolicyDecision | None,
executed: ExecutedResponse | None`.

## `/agents`

Read-only view onto the agent-trace table. **Deliberately no endpoint to
run an agent** — no real LLM backend is wired in anywhere in this codebase
yet (see `backend/app/agents/README.md`), so an endpoint that "ran" one
could only replay `MockLLMClient`'s scripted responses, which the project
has chosen not to expose as if it were real functionality.

| Method | Path | Purpose | Response |
| --- | --- | --- | --- |
| GET | `/agents?incident_id=&agent_name=` | Every recorded agent-call trace, optionally filtered | `list[AgentTraceOut]` |
| GET | `/agents/{incident_id}` | Every trace for one incident | `list[AgentTraceOut]` |

`AgentTraceOut`: `incident_id, agent_name, input_payload: dict,
output_payload: dict | None, succeeded: bool, recorded_at: str, error: str |
None`. Empty list, never fabricated, when nothing has run for the filter —
the dashboard's "not-run, not blank" requirement starts here.

## `/risk-assessments`

Thin, stateless wrapper over `RuleBasedRiskModel.calculate_risk` — no risk
assessment is persisted anywhere (Section 8's storage table names no such
table; a `RiskScore` only feeds the next step).

| Method | Path | Purpose | Response |
| --- | --- | --- | --- |
| POST | `/risk-assessments` | Compute a `RiskScore` from a threat assessment, clinical context, and candidate actions | `RiskScore`, 400 on empty `candidate_responses` or an incident-id mismatch between `threat`/`context` |

Request body (`RiskAssessmentRequest`): `threat: ThreatAssessment, context:
ClinicalContext, candidate_responses: list[CandidateAction]`. Because no
orchestrator exists to fetch an incident's agent outputs automatically, the
caller must supply `threat`/`context` directly — there is no `incident_id`-
only variant of this endpoint.

`RiskScore` (`backend/app/schemas/risk.py`): `cyber_risk: float,
clinical_risk: float, response_impact: dict[str, ImpactLevel]` — note this
is a categorical `ImpactLevel` enum keyed by action, **not** the `dict[str,
float]` the architecture spec's §12 literally describes (a disclosed Phase 5
schema divergence; see `docs/phase15-verification.md`).

## `/responses`

L6 (Policy Engine) and L7 (Response Orchestrator) over HTTP.

| Method | Path | Purpose | Response |
| --- | --- | --- | --- |
| POST | `/responses/proposed` | Evaluate a proposed response against the Policy Engine's rule table | `PolicyDecision`, 201; 400 on a `PolicyEngine.evaluate` `ValueError` |
| GET | `/responses/proposed` | List every pending policy decision | `list[PolicyDecision]` |
| GET | `/responses/proposed/{incident_id}` | One incident's pending decision | `PolicyDecision`, 404 if none pending |
| POST | `/responses/executed` | Execute whichever `PolicyDecision` is pending for an incident | `ExecutedResponse`, 201 |
| GET | `/responses/executed` | List every executed response | `list[ExecutedResponse]` |
| GET | `/responses/executed/{incident_id}` | Executed responses for one incident | `list[ExecutedResponse]` |

`POST /responses/proposed` request (`ProposeResponseRequest`): `risk_score:
RiskScore, proposed_response: ProposedResponse, context: ClinicalContext`.
Side effects on success: stores the `PolicyDecision` in
`ProposedResponseRepository`, enqueues `DecisionProvenance`.

`POST /responses/executed` request (`ExecuteResponseRequest`): `incident_id:
str, approval: ApprovalRecord | None`. This is **the one endpoint in the
entire API that can mutate simulated device state** — it is the only call
site anywhere that invokes `ResponseOrchestrator.execute`. Failure modes,
each mapped to a distinct status code: 404 if no decision is pending for
that incident, or if the incident/device no longer exists; 409 if the
decision requires approval but none was supplied
(`ApprovalRequiredError`), or if the supplied approval rejected the action
(`ResponseRejectedError`); 400 on other `ValueError`s; **501** if the chosen
action category has no implemented device-mutation effect yet (disclosed
gap: four `ResponseActionCategory` values — session/credential/backup/
failover-related — have no mechanism in the simulator). On success,
records the `ExecutedResponse`, removes the now-stale `PolicyDecision`,
enqueues `ResponseProvenance` and (if an approval was supplied)
`ApprovalProvenance`.

## `/recovery`

L8 over HTTP. Does not call the Recovery Verification Agent itself (same
reasoning as `/risk-assessments`: no orchestrator exists yet to produce a
`RecoveryResult` automatically) — the caller supplies one directly.

| Method | Path | Purpose | Response |
| --- | --- | --- | --- |
| POST | `/recovery` | Process a `RecoveryResult`, transitioning the incident to `resolved` or `reopened` | `Incident`; 404 if incident unknown; 409 (`InconsistentRecoveryResultError`) if the result's fields can't be routed, though the evidence is still recorded |
| GET | `/recovery` | List every recovery result | `list[RecoveryResult]` |
| GET | `/recovery/{incident_id}` | Recovery results for one incident | `list[RecoveryResult]` |

Request body is `RecoveryResult` (`backend/app/schemas/agents.py`) directly,
no wrapper. On success, also enqueues `RecoveryProvenance` (with
`residual_threats_hash` set only if `residual_threats` is non-empty).

## `/blockchain/audit`

Read-only listing over the outbox, plus one manual action trigger.

| Method | Path | Purpose | Response |
| --- | --- | --- | --- |
| GET | `/blockchain/audit?incident_id=&status=` | List outbox entries, optionally filtered | `list[OutboxEntryOut]` |
| GET | `/blockchain/audit/{incident_id}` | Outbox entries for one incident | `list[OutboxEntryOut]` |
| POST | `/blockchain/audit/process` | Drain every currently-`PENDING` entry once, against whichever `FabricClient` the process is configured with (mock by default) | `list[OutboxEntryOut]` (the processed entries) |

`OutboxEntryOut`: `id: int, record_type: OutboxRecordType, payload: dict,
created_at: datetime, status: OutboxStatus, chain_tx_id: str | None,
attempts: int, last_error: str | None, updated_at: datetime`. A
`chain_tx_id` of `None` with `status="pending"` means "not yet committed" —
a visible state, never hidden, per architecture spec §14.

`POST /blockchain/audit/process` is a **manual trigger** — nothing in
`app_factory.py` starts a background drain loop; a real deployment would run
`OutboxWorker.run_forever()` itself, which this endpoint does not do.

## Error shape

FastAPI's default `{"detail": "..."}` JSON body on every `HTTPException`
raised above; no custom error envelope. Status codes used across the API:
200/201 (success), 400 (bad request — a rejected `ValueError`), 404 (not
found), 409 (conflict — a state the request can't be applied to right now,
such as a required approval not yet given), 501 (understood but not
implemented for this specific action category), 503 (a required artifact,
e.g. a trained model, doesn't exist yet).
