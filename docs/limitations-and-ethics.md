# Limitations, ethics, and safety

This document collects, in one place, every disclosed gap and scope
boundary that is otherwise scattered across module READMEs,
`docs/security-checklist.md`, `docs/phase15-verification.md`, and the root
`README.md`. Nothing here is new information — it is a single honest
accounting, written so a reader doesn't have to assemble it themselves from
a dozen files. Where the master plan is explicit that this project makes no
clinical-safety claim, that intent is quoted, not paraphrased into
something stronger.

## 1. This is a research prototype, not a clinical or safety-certified system

The master plan's own framing (plan §2/§30, as described to the agents
building this project) is explicit: this is a research artifact built to
study a decision-making question — whether jointly weighing cyber risk and
clinical/patient impact changes response behavior in a measurable,
beneficial way — not a product intended for deployment against real
patients or real hospital infrastructure. Nothing in this repository
contradicts that framing: there is no FDA/CE/clinical-trial pathway
artifact anywhere in this codebase, no real patient data was ever processed
(every `patient_id` is synthetic, generated by the simulator), and no claim
of clinical validation exists anywhere in `docs/` or any module README.
**This system makes no claim, implicit or explicit, of being safe to
connect to a real medical device or a real hospital network.** Anyone
building on this code for anything beyond research/education should treat
every "safety" mechanism described here (the Policy Engine's rule table,
the dual-risk model) as a research demonstration of a *decision-making
pattern*, not a certified safety control.

## 2. Simulation-only scope — nothing here touches real infrastructure

- **No real IoMT device, protocol, or network exists in this codebase.**
  The "infusion pump," "ventilator," and "ECG monitor" are
  `SimulatedDevice` Python objects (`backend/app/iomt_simulator/device.py`)
  with no network interface, no firmware, and no physical counterpart.
  "Executing a response" means calling a method on that Python object, not
  touching a real device.
- **No real attack ever occurs.** Every attack is a scripted
  `AttackInjection` (`backend/app/iomt_simulator/scenario.py`) or a labeled
  row in a dataset — see §3 below for what that dataset actually is.
- **The Response Orchestrator's own module docstring states this directly**:
  it is "the only function anywhere in this codebase that calls a
  `SimulatedDevice` mutation method" — confirming there is no other path
  to anything resembling a real-world effect.

## 3. Training/evaluation data is synthetic, not the real named datasets

- **No real CICIoMT2024 or WUSTL-EHMS-2020 data has ever been used.** Every
  trained detection model in this repository, and every number in
  `evaluation/phase13_baseline_comparison.md`, is trained and evaluated
  against `backend/app/cybersecurity/synthetic_data.py`'s synthetic
  stand-in — a dataset generated to match the *feature family* CICIoMT2024
  is documented to have, not a verified transcription of its real columns
  (that module's own docstring is explicit that the exact column names were
  never independently confirmed against a real downloaded CSV).
- **Why:** this project's development sandbox has no network route to
  `unb.ca` or the CIC research mirror (`datasets/LICENSE_NOTES.md`) — not a
  judgment call to skip real data, a disclosed environmental constraint.
  `datasets/download_ciciomt2024.py` exists and is written to run on a
  machine with real internet access, but has never actually been run.
- **`training.py`'s `load_real_dataset()` deliberately raises
  `NotImplementedError`** rather than guess at a loader for data that was
  never available to test against (re-confirmed in
  `docs/phase15-verification.md`).
- **Consequence for every reported metric**: the Phase 13 evaluation's
  headline numbers (0/162 vs. 162/162 unsafe-autonomous-action rate) are
  real, honestly-computed numbers — on synthetic data. They demonstrate
  that the patient-aware policy layer changes behavior in the intended
  direction on data shaped like the real thing; they are not evidence of a
  specific detection accuracy, false-positive rate, or safety margin on
  real IoMT network traffic. Treat every number in `evaluation/` as "what
  this architecture does on a controlled synthetic benchmark," not as
  "field-measured performance."
- **One metric could not even be measured on this data**:
  `unnecessary_isolation_rate` has a `0/0` denominator in the Phase 13 run
  because the synthetic dataset's classes are Gaussian-separated by
  construction and both trained detectors measured zero false positives —
  a property of the synthetic data, not of the detection approach.

## 4. No real LLM backend — every agent is schema-validated, never model-validated against a live model

- **`LLMClient` is an interface; `MockLLMClient` is the only implementation
  anywhere in this codebase** (`backend/app/agents/llm_client.py`). No real
  LLM API call has ever been made by this project's agent code.
- **Every "agent output" in every test, every integration test, and the
  Phase 13 evaluation harness is either `MockLLMClient`'s scripted response
  or a small, named, deterministic stand-in function**
  (`backend/app/evaluation/baseline_systems.py`'s own docstring: the
  Threat Reasoning, Healthcare Context, and Response Planning agents in
  the evaluation harness are "stood in for by small, named, deterministic
  functions, each one an honest restatement of a trial's real ground
  truth, never an arbitrary or hand-tuned value").
- **No orchestration layer sequences the five agents automatically.**
  Wherever the five agents run together (the lifecycle integration test,
  the Phase 11 E2E seeding, the evaluation harness), they are called
  manually, by hand, in that test/script's own code — not through a real
  multi-agent framework or scheduler.
- **Consequence:** this project demonstrates the *schema and tool-boundary
  design* for agentic reasoning (structured I/O, a fixed read-only tool
  allowlist, retry-once-then-fail validation) — it does not demonstrate
  that a real LLM, given these schemas and tools, actually produces sound
  investigation/threat/clinical-context judgments. That is untested.

## 5. Narrower attack-type coverage than the master plan originally scoped

`AttackCategory` (`backend/app/schemas/enums.py`) covers exactly seven
values: `dos`, `ddos`, `reconnaissance`, `mqtt_based`, `spoofing`,
`mitm_injection`, `unknown`. Malware/ransomware behavior and ARP spoofing
specifically are named in `docs/architecture.md` §10 as deferred — "no
dataset candidate reviewed so far labels them with adequate sample sizes" —
and remain deferred; no code path anywhere scores or labels either. ECU-IoHT
(a third candidate dataset) was never downloaded or evaluated at all. This
is a narrower attack surface than a full healthcare-IoMT threat model would
eventually need to cover.

## 6. Authentication is real but opt-in; rate limiting is still absent

**Post-Phase-15 update:** a real, API-key-based authentication/authorization
layer now exists (`backend/app/core/auth.py`, three ranked roles —
`viewer` < `operator` < `approver`) and is wired globally onto every router
except `/health`. It defaults to **disabled**
(`Settings.auth_enabled=False`) — the same permissive, no-credential
behavior this system has always had — so running it locally with no
configuration is still exactly as open as before. Set `AUTH_ENABLED=true`
plus real `API_KEYS` (see `.env.example`) before exposing this to anything
beyond a trusted local network; enabling it with no keys configured fails
closed (every non-health route returns 401), never silently open.

No rate-limiting or request-size-limiting middleware exists anywhere in the
backend (`docs/security-checklist.md` §5, confirmed by grep for
`slowapi`/custom limiters/`max_content_length`) — a real, disclosed, still
open gap independent of the auth layer above. This system should not be
exposed to an untrusted network regardless of `AUTH_ENABLED` until that is
addressed too.

## 7. No multi-agent orchestration, no live push/polling, no background blockchain drain loop

- Detection, response execution, and recovery verification are all
  on-demand HTTP calls, not an always-on autonomous loop.
- The dashboard reads on page load/user action; there is no WebSocket or
  polling push mechanism.
- `OutboxWorker.run_forever()` exists but nothing in `app_factory.py`
  starts it — blockchain writes stay `pending` until a human or test calls
  `POST /blockchain/audit/process`.

None of this is hidden "it just doesn't run yet" — each is a named,
deliberate phase-boundary decision (see each router's own module docstring
and `docs/phase15-verification.md`), not a bug.

## 8. Storage is mostly in-memory; what "Postgres-backed" actually means here

A real, scope-limited Postgres migration exists (`backend/app/models/
orm.py`), but it covers only six relational tables
(`incidents, agent_traces, recovery_results, proposed_responses,
executed_responses, outbox_entries`). `NetworkEventStore`/`TelemetryStore`
(device telemetry and network/security events — Section 8's separate
TimescaleDB-hypertable category) and the live `DeviceRegistry` remain
in-memory regardless of `REPOSITORY_BACKEND`, and are lost on process
restart. There is no Alembic migration tool — only additive `create_all`.
The Postgres driver is synchronous (`psycopg`), a deliberate, disclosed
tradeoff that blocks the event loop during a DB call; acceptable for this
prototype's scale, not for a production, high-concurrency deployment.

## 9. Docker/deployment has never been run-verified in this project's own history

`docker-compose.yml`, `backend/Dockerfile`, and `frontend/Dockerfile` have
never completed a real `docker compose up --build` inside this project's
development sandbox — every container registry tried from it returned 403
Forbidden. Only `docker compose config`'s syntax/variable-interpolation
check has actually run. See `docs/deployment.md` §0 for the full
disclosure; this is a constraint of this project's own dev history, not a
statement about Docker in general.

## 10. No independent / third-party review

Every disclosure in this document and in `docs/security-checklist.md` was
produced by the same project (the agents and the person building it), by
reading the real code and re-running real test/scan commands — not by an
external auditor, a clinical-safety reviewer, or a penetration tester. Real
findings were really fixed where found (e.g. the Phase 12 `pip-audit`
CVEs), and real gaps were disclosed rather than hidden, but "we checked our
own work carefully" is not a substitute for independent review, especially
for anything touching patient safety.

## Summary table

| --- | --- | --- |
| Clinical/safety certification | A research demonstration of patient-aware decision routing | Any clinical validation, certification, or claim of real-world safety |
| IoMT devices/network | Simulated Python state machines | Any real device, protocol, or network |
| Detection training data | A synthetic stand-in matching CICIoMT2024's feature family | Real CICIoMT2024, WUSTL-EHMS-2020, or ECU-IoHT data |

| Persistence | 6 tables optionally Postgres-backed | Telemetry/events/device-registry persistence, DB migrations |
| Deployment | Config-validated Docker Compose, native-binary Fabric | A completed, registry-verified `docker compose up` anywhere in this project's history |
| Review | Self-disclosed, self-verified | Independent/clinical/security audit |
